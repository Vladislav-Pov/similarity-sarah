# AIDE ML интеграция — Подэтап 6.1: Discovery

> Decision-grade discovery. Цель — понять, подходит ли AIDE ML (arXiv:2502.13138) как
> инструмент для тюнинга и улучшения нашего inexact-proximal-солвера внутри NFG-SS, либо
> нужен другой класс инструмента. Источники: четыре отчёта (A — репо AIDE, B — статья AIDE,
> C — аудит нашего prox-сабсистемы, D — альтернативы). Ключевые цитаты из (C) перепроверены
> по живому коду этого репозитория (см. Приложение).

## 1. Архитектура AIDE (mental model)

AIDE — это LLM-агент, который формулирует ML-инжиниринг как оптимизацию кода: максимизировать
скалярную целевую функцию `h(s)` над пространством Python-скриптов через **tree search**. В его
терминах **task** — это чистый естественный язык: строка `goal` плюс опциональная строка `eval`
(как оценивать), либо `desc_file`; машиночитаемой спецификации задачи нет — `load_task_desc`
просто упаковывает их в `{"Task goal": ..., "Task evaluation": ...}` и отдаёт LLM как текст
промпта. **Solution** — это `Node` (`aide/journal.py`): самодостаточный однофайловый Python-скрипт
(`code`), NL-`plan`, перехваченный stdout/stderr, инфо об исключении и метрика. Множество узлов
образует `Journal` (дерево решений). **Score** — это `MetricValue(value: float, maximize: bool)`;
багнутым узлам присваивается `WorstMetricValue` (всегда проигрывает в сравнении). Поиск (`Agent.search_policy`)
— это жёстко зашитый цикл DRAFT → DEBUG → IMPROVE: пока не набрана квота черновиков (`num_drafts=5`)
— генерируй новый draft; иначе с вероятностью `debug_prob=0.5` чини случайный багнутый лист в пределах
`max_debug_depth=3`; иначе жадно улучшай лучший небагнутый узел (`get_best_node()`).

Два момента критичны для нашей задачи. **(1) Score НЕ вычисляется пользовательским эвалюатором.**
Агент запускает сгенерированный скрипт в подпроцессе (`Interpreter.run`, `exec(compile(...))`),
а затем **второй LLM-вызов** («feedback» модель, по умолчанию `gpt-4.1-mini`) читает stdout
программы и через forced function-call `submit_review` *извлекает* метрику: `node.metric =
MetricValue(response["metric"], maximize=not lower_is_better)`. То есть истинность score — это то
число, которое скрипт напечатал в stdout, и которому поверил LLM-судья. Grep по `aide/**.py`
не нашёл ни одного хука для регистрации своего детерминированного score-функции / evaluator-класса
/ ground-truth harness. **(2) Целевой код — однофайловый Kaggle-стиль.** Промпты жёстко зашиты:
«single-file python program that is self-contained and can be executed as-is», «print the value of
the evaluation metric on a hold-out validation set», сохранить `submission.csv` в `./working`,
данные в `./input`; `_draft` начинается с «You are a Kaggle grandmaster». Нет поддержки
многофайловых проектов, нет распределённого/многопроцессного harness (код исполняется одним `exec`
в одном дочернем процессе), нет понятия вложенного/inexact внутреннего солвера. **Запуск требует
LLM-ключа** (хотя бы один из OpenAI/Anthropic/Gemini/OpenRouter; не-LLM режима нет); установка
`pip install -U aideml`, CLI `aide` или Python `aide.Experiment(...).run(steps=N)`.

**Итог mental model:** custom score-функции — НЕ поддерживаются (только английская строка `eval=`
+ выбор feedback-LLM); целевой артефакт — однофайловое Kaggle-решение, печатающее одно число,
а НЕ произвольный многофайловый/распределённый код.

## 2. Наша проблема: где реально больно

Аудит (C) статически разобрал prox-сабсистему NFG-SS. Конкретные болевые точки (цитаты
перепроверены по живому коду этого репо):

1. **Невидимый эффективный inner-LR (auto-gamma0).** `_resolve_lr` (`similarity_sarah/prox/accvrs.py:80-84`)
   при `prox_lr=null` возвращает `(1/(2*(1+theta*L1)))*lr_factor`. Для best-конфига
   (`theta=0.2, L1=200, lr_factor=0.1`) это `(1/(2*41))*0.1 = 1.22e-3` — число, которого НЕТ
   ни в одном конфиге, его надо считать руками из четырёх полей. `L1=200` — это Lipschitz-оценка
   `f1`, унаследованная из ДРУГОГО сетапа репозитория AccVRS (`docs/ACCVRS_PROX_SOLVER.md:207`
   «У нас сетап другой»), то есть угаданная, а не измеренная для нашего CIFAR/ResNet/partition.

2. **`theta` — двойного назначения.** Один и тот же `theta` задаёт внешний prox-target
   (`z = w - theta*v`, `nfg_ss.py:183`) И входит в auto-LR (`L = 1 + theta*L1`,
   `accvrs.py:83`). Поэтому ретюнинг `theta` молча ретюнит внутренний шаг — связь, которую
   невозможно увидеть из конфига.

3. **Latent scheduler-баг / no-op.** `runtime/loop.py` применяет `prox_lr_schedule` только когда
   `solver.lr` не-None; но best-конфиг использует `prox_lr=null`, так что весь `prox_lr_schedule`
   на AccVRS-пути **молча игнорируется** (а reference-JSON всё равно везут `prox_lr_schedule:
   {kind: constant}` — no-op). Если же выставить явный `prox_lr` чтобы включить расписание,
   `lr_factor` применяется ДВАЖДЫ (в `loop.py`, затем снова в `accvrs.py:82`). Foot-gun.

4. **Диагностика не измеряет сходимость для выигрышного солвера.** `prox_grad_norm_ratio`
   (`_diag.py`) меряет сходимость к каноническому argmin `Phi` (с членом `theta*v`). Но reference
   AccVRS-путь ОПУСКАЕТ `theta*v` из направления (`include_linear_term=false`, `accvrs.py:143-149`),
   сходясь к v-free точке — НЕ к тому argmin, что меряет метрика. Ненулевой ratio тут не означает
   «недосходился». Плюс `instructions.md:164` отдельно предупреждает, что под `v_schedule=linear`
   ratio «может остаться near 1» и неинформативен. Три reference-JSON — config-only, метрик не хранят,
   так что эмпирических данных о сходимости inner-solve на опубликованных прогонах вообще НЕТ.

5. **Реальный риск under-solve, который трудно увидеть.** `prox_num_steps=4` считает ПОЛНЫЕ ПРОХОДЫ
   по server-loader, а не итерации (`accvrs.py`); при ~40 батчах/проход это лишь ~160 inner-SGD
   итераций на prox-вызов. `docs/ACCVRS_PROX_SOLVER.md:182-221` явно фиксирует обе ловушки:
   «слишком мало итераций» и преждевременный early-stop (1e-4, проверяется каждые 8 шагов против
   шумной нормы тренировочного батча, а не против eval-нормы `||grad Phi||`).

**Подтверждённый факт (grep по `configs/search/`):** автоматический поиск (`optuna_bnfg.yaml`,
`grid_bnfg.yaml`) свипает только `theta/prox_lr/prox_num_steps/v_schedule` и НЕ содержит
AccVRS-специфичных ручек (`L1, lr_factor, momentum, weight_decay, early_stop, decay`) — тех самых,
на которых держится best.yaml. То есть самые load-bearing параметры выигрышного конфига выставлены
руками/гридом ВНЕ автоматического поиска.

### Вердикт о bottleneck

**Bottleneck = HP-SEARCH / CONFIGURABILITY, НЕ solver-code и НЕ GPU-throughput.** Сам солвер
маленький (~230 строк), корректный, bit-reproducible (по MEMORY), а per-call overhead — лишь дешёвый
диагностический forward/backward. Боль в том, что ~12 связанных ручек схлопываются в две эффективные
величины (inner-LR и inner-iteration-count) через неочевидную арифметику, а самые важные из них даже
не входят в search-space. Это значит: нам нужен прежде всего **более умный/широкий HP-поиск** (плюс,
возможно, генерация новых правил inner-loop), а НЕ Kaggle-стиль автор однофайловых скриптов.

## 4. Рекомендация

**Вердикт: «остаёмся на Optuna — AIDE избыточен» (для текущего сабэтапа).**

Аудит (C) однозначно показал, что наш bottleneck — это **HP-search / configurability**, а не
дефицит вариантов кода солвера и не throughput. А самая большая дешёвая победа лежит прямо в
Optuna, который у нас уже есть и который воспроизводим/локален/бесплатен: расширить search-space
на AccVRS-ручки (`L1, lr_factor, momentum, weight_decay, early_stop, decay`), которых там сейчас
просто нет (подтверждено grep'ом по `configs/search/`), добавить conditional define-by-run по
`prox_solver = {sgd, adam, accvrs}`, и при желании multi-objective (accuracy vs comm-rounds vs
wall-clock) с ASHA-прунингом. Это закрывает 4 из 5 болей раздела 2 без единого доллара на API и
без нового недетерминированного судьи в цикле.

AIDE здесь — неправильный класс инструмента: его score извлекается LLM из stdout (нет хука под наш
детерминированный golden-oracle), его целевой артефакт — однофайловое Kaggle-решение, и у него нет
понятия вложенного inexact-солвера. Завести его на нашу задачу = переписать `agent.py` и промпты
под наш harness, при этом получив МЕНЕЕ воспроизводимый score, чем уже есть. Если позже мы решим,
что нам мало числового тюнинга и нужны **генуинно новые правила** inner-loop (новый stopping-criterion,
новый warm-start, новое update-rule) — то правильный инструмент не AIDE, а **OpenEvolve**: он строится
вокруг `EVOLVE-BLOCK` + custom-evaluator (наш golden-oracle ложится напрямую), умеет локальный LLM
(~$0) и относится к той же категории code-search, что и AIDE, но с лучше подходящим контрактом.

**Уверенность: средняя.** Аудит был статическим — ни одного прогона; конкретных значений
`prox_grad_norm_ratio`/`prox_obj_decrease` на reference-конфиге мы не наблюдали (reference-JSON их
не хранят). **Единственный факт, который перевернул бы рекомендацию:** если эмпирический прогон
покажет, что расширенный Optuna-свип НЕ может достичь целевого качества ни при каких числовых HP
(т.е. ограничение реально в форме update-rule, а не в значениях) — тогда нужен code-gen слой, и
выбор смещается к OpenEvolve (а не к AIDE).

## 5. Открытые вопросы к пользователю перед 6.2

1. **Числа или код?** Нам реально нужны генуинно НОВЫЕ варианты кода inner-solver (новый
   stopping-criterion, warm-start, update-rule), или достаточно лучше **просвипать числовые HP** уже
   написанного AccVRS? (Это определяет: Optuna-расширение vs OpenEvolve-слой; AIDE не выигрывает ни в
   одном из сценариев.)

2. **Бюджет на API.** Готов ли тратить деньги/ключи на LLM-цикл? Если бюджет ≈ $0 — отпадает AIDE
   как есть, а OpenEvolve остаётся только на ЛОКАЛЬНОЙ модели (Ollama/vLLM). Если бюджет есть —
   насколько (десятки $ за сабэтап достаточно для сотен итераций)?

3. **Что считаем bottleneck по ощущениям — скорость или качество?** Аудит говорит «качество/конфиг».
   Совпадает ли это с твоим опытом прогонов, или ты упираешься в wall-clock на A100 (тогда разговор
   совсем другой — ни AIDE, ни Optuna throughput не лечат)?

4. **Доверяем ли мы golden-oracle как evaluator-у?** И OpenEvolve, и любой осмысленный поиск
   опираются на детерминированный fitness. Готовы ли мы зафиксировать текущий golden + metrics
   harness как единственный источник истины для score? (Если score сам спорный — сначала чиним его.)

5. **Чиним ли сначала диагностику?** `prox_grad_norm_ratio` структурно не меряет сходимость для
   `include_linear_term=false` пути (раздел 2, п.4). Любой автоматический поиск, опирающийся на этот
   сигнал, будет оптимизировать не туда. Чиним диагностику ДО запуска поиска, или ищем по
   end-метрике (accuracy) и игнорируем inner-ratio?
